# Market Cache Design Proposal

## 1. Статус и область

- Статус: proposed for M1.5 implementation review.
- Дата: 2026-08-03.
- Архитектурное основание: ADR-016.

Документ определяет минимальный Market Cache для свечей. Он не проектирует стратегии, индикаторы, polling, WebSocket, database persistence или торговые решения.

## 2. Назначение

Market Cache принимает уже нормализованные и проверенные `Candle` и предоставляет единый внутренний read path для всех режимов работы:

```text
MarketProvider -> Validation -> Market Cache -> Internal consumers
```

Market Cache не знает, поступили данные от Binance, replay или другого provider. Он не выполняет ввод-вывод и не содержит торговой логики.

## 3. Минимальная модель

### Stream key

Ключ потока состоит из:

- `symbol` — непустой нормализованный идентификатор инструмента, например `BTCUSDT`;
- `interval` — непустая каноническая строка интервала, например `1m`.

Концептуальный тип: `MarketStreamKey(symbol, interval)`. Он должен быть immutable, hashable и независим от Binance. Нормализация внешнего символа и интервала выполняется до обращения к cache.

### Capacity

Рекомендуемая начальная ёмкость — **1000 свечей на поток**. Ёмкость задаётся при создании cache как положительное целое число и одинакова для всех потоков в минимальной реализации.

После превышения ёмкости удаляется самая старая свеча соответствующего потока. Потоки не влияют на ёмкость друг друга. Неограниченный режим не поддерживается.

## 4. Proposed contract

Минимальный типизированный контракт должен выражать следующие операции без привязки к конкретным именам Python-методов:

### Insert or update

Вход:

- `MarketStreamKey`;
- одна проверенная `Candle`;
- явный `observed_at_ms`, необходимый для воспроизводимого определения закрытости.

Результат сообщает один из исходов: `inserted`, `updated` или `unchanged`. Метод не публикует события и не вызывает внешние компоненты.

### Read last N

Вход:

- `MarketStreamKey`;
- положительное `limit`;
- флаг включения текущей незакрытой свечи.

Результат — immutable snapshot не более чем из `N` свечей в строгом порядке `open_time_ms`. Если поток отсутствует или пуст, возвращается пустой snapshot.

### Read latest closed

Вход:

- `MarketStreamKey`;
- явный `as_of_ms`.

Результат — последняя свеча, для которой `close_time_ms < as_of_ms`, либо `None`, если закрытых свечей нет. Пустой cache в данном случае не считается исключительной ситуацией.

### Inspect stream

Минимально допустима read-only операция получения размера потока. Дополнительная статистика cache не входит в M1.5.

## 5. Правила вставки

1. Новая свеча проходит существующую проверку одной `Candle` до изменения состояния cache.
2. Первая свеча создаёт поток для указанного ключа.
3. Свеча с `open_time_ms` больше последней принимается только при соблюдении ожидаемой последовательности интервала и отсутствии пересечения диапазонов.
4. При превышении capacity удаляется самая старая свеча потока.
5. Операция атомарна на уровне одного cache: при ошибке состояние не меняется.

Полная batch-валидация остаётся обязанностью Validation. Cache повторно проверяет только инварианты, необходимые для защиты собственного состояния при инкрементальной записи.

## 6. Duplicate и update semantics

### Exact duplicate

Если ключ, `open_time_ms` и все поля свечи совпадают, операция идемпотентна: состояние не меняется, возвращается `unchanged`.

### Conflicting duplicate

Если `open_time_ms` совпадает, но поля различаются:

- последнюю незакрытую свечу разрешено заменить более свежей версией;
- закрытая свеча immutable и конфликт отклоняется;
- изменить свечу, которая не является последней, нельзя.

Определение незакрытости использует переданный `observed_at_ms`, а не скрытое системное время. Внутренний entry отдельно хранит подтверждённость закрытия: наступление wall/exchange time само по себе не делает ранее открытую версию immutable до успешного cache commit.

Переходы первой реализации:

- insert при `observed_at_ms <= close_time_ms` сохраняет `OPEN`;
- insert после boundary сразу сохраняет `CLOSED_CONFIRMED`;
- `OPEN` допускает monotonic refresh и один финальный update;
- exact duplicate `OPEN` после boundary атомарно подтверждает закрытие;
- финальный update после boundary атомарно меняет данные и подтверждает закрытие;
- `CLOSED_CONFIRMED` принимает только exact duplicate.

Lifecycle metadata не входит в public `Candle` snapshot. `MarketCacheChange` содержит additive flags `previous_closed_confirmed`, `current_closed_confirmed`, `data_changed` и `closure_confirmed`.

### Out-of-order

Свеча с `open_time_ms` меньше времени последней сохранённой свечи отклоняется. M1.5 не выполняет историческую вставку в середину и не сортирует входные данные автоматически.

### Gap

Если новая свеча открывается не в ожидаемый следующий момент, вставка отклоняется типизированной ошибкой. Cache не загружает отсутствующие данные самостоятельно.

## 7. Read semantics

- Результаты всегда отсортированы по возрастанию `open_time_ms`.
- Чтение возвращает immutable snapshot, чтобы потребитель не мог изменить внутреннее состояние.
- `limit` должен быть положительным; значение больше capacity допустимо и возвращает все доступные свечи.
- Отсутствующий или пустой поток возвращает пустой snapshot для `last N` и `None` для `latest closed`.
- Чтение не инициирует загрузку данных и не ожидает их появления.

## 8. Thread safety

Для M1.5 thread-safety **не требуется**. Утверждённый первый market loop синхронный, с одним writer и последовательным чтением в одном процессе.

Минимальная реализация должна явно документировать, что она не thread-safe. Блокировки не добавляются заранее. Переход к `asyncio`, WebSocket, нескольким writer или конкурентному чтению требует review контракта и отдельного ADR.

## 9. Storage and persistence

M1.5 использует только bounded in-memory storage. Market Cache не гарантирует сохранность после перезапуска и не взаимодействует с SQLite.

Будущая persistence является отдельным адаптером и не должна менять интерфейс чтения cache. Восстановление cache из persistence не входит в M1.5.

## 10. Типизированные ошибки

Предлагаемая минимальная иерархия:

- `MarketCacheError` — базовая ошибка cache;
- `MarketCacheConfigurationError` — некорректная capacity;
- `MarketStreamKeyError` — некорректный symbol или interval в ключе;
- `MarketCacheConflictError` — конфликтующий duplicate или попытка изменить закрытую свечу;
- `MarketCacheOutOfOrderError` — запись старее последней сохранённой свечи;
- `MarketCacheGapError` — нарушение ожидаемого следующего интервала;
- `MarketCacheReadError` — некорректный read limit или параметры чтения.

Ошибки качества самой `Candle` остаются в существующей иерархии `MarketDataValidationError` и не дублируются cache-ошибками.

Пустой cache не вызывает ошибку, поэтому отдельный `MarketCacheEmptyError` в минимальном контракте не нужен.

## 11. Инварианты

Для каждого потока cache гарантирует:

- размер не превышает capacity;
- свечи строго упорядочены по `open_time_ms`;
- дубликаты `open_time_ms` отсутствуют;
- временные диапазоны не пересекаются;
- между соседними свечами нет неявно принятого gap;
- закрытые свечи не изменяются;
- незакрытой может быть только последняя свеча;
- потребитель не может изменить внутреннее состояние через read result.

## 12. Открытые вопросы M1.5 review

1. Должна ли capacity настраиваться глобально или отдельно для каждого потока после минимальной реализации.
2. Нужна ли отдельная операция атомарной batch-загрузки для начального bootstrap или достаточно последовательной вставки после batch-валидации.
3. Должна ли конфликтующая версия незакрытой свечи дополнительно требовать неубывающий volume.
4. Нужен ли read-фильтр по временному диапазону уже в M1.5 или его следует отложить.
5. Следует ли возвращать отдельный тип `InsertResult` или минимальный enum результата.

## 13. Рекомендуемая минимальная реализация M1.5

- Один in-memory класс с `dict[MarketStreamKey, bounded sequence]`.
- `deque` с `maxlen=1000` или эквивалентная структура с явной capacity.
- Immutable `MarketStreamKey`.
- Три публичные операции: insert/update, last N, latest closed.
- Явные `observed_at_ms` и `as_of_ms`; скрытое системное время не используется.
- Один writer, без locks и async primitives.
- Защитные immutable snapshots на чтении.
- Unit-тесты всех insert/update/read/error semantics и независимости потоков.
